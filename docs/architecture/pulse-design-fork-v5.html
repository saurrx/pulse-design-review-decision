Pulse / Design operations / Proposal

Pulse Design Fork

One design repository, forked from today's production frontend, running on mock data, where the Pulse v4 redesign is built for all six roles and handed back as patches the developer can apply in an afternoon. Nothing in this document has been built yet.

Date 3 Sep 2026 Frontend baseline pulse-frontend df5f2ff Backend baseline pulse-backend 00272d1 Atlas ec1411b Redesign target PL-TKN-004 (Pulse v4)
Summary

The short version

The last design port, PR #2 on 28 August, was expensive because the design repo had drifted from production in three ways at once: an older fork point, the old API dialect and role names, and four endpoints the backend did not have. Every constraint you have set since is a reaction to that. The fix is to make the design repo a fork of production itself and to keep it that way.

  • Fork production at its head, file for file, into a private design repo. The permanent mock and review infrastructure stays outside src/; portable token sources, generated styles and product UI changes stay inside the production-shaped tree. Sync from production daily while it moves this fast.
  • Mock at the network, under the adapter, with Mock Service Worker. The app's own login, cookie, adapter and React Query code runs unchanged. A mock route is only allowed if it exists in the backend's pinned route map, which is how "no backend changes" becomes a CI failure instead of a review comment.
  • Reuse the developer's own instruments. Production already has a structural conformance baseline per role and page, layout invariants, a role lint and a route map. They run against the mock app on every design PR, with no login throttle in the way.
  • Storybook from the first commit, sharing the mock scenarios and the provider tree with the full app. Every role, state and screen gets a stable story URL, and every design record names the stories it changed and carries their visual, interaction and accessibility results. Verified feasible on the frozen stack: Storybook 10.6 and Vitest 3.2 both accept Vite 5; Vitest 4 does not.
  • Hand off a patch and a note. Each design change is a numbered record with an exported patch built from portable product paths only, screenshots per role, and a machine-generated list of what moved structurally. Stories, scenarios and the record itself travel beside the patch, never inside it. The developer applies it three-way and re-records the baseline.
  • Own the instruction files. Production's CLAUDE.md forbids visual change and names live infrastructure, so the design repo carries its own root file with an explicit precedence statement and keeps production's under contract/, synced and reported but never loaded.
  • Spike two screens first. The review queue and the login screen, in the full app and in Storybook, with the export applied to production, before the full route surface and story catalogue are built.
  • Make production themeable first. Four in five colour decisions in production are literals inside 2,000-line screens, and 750 dead dark-theme branches sit in 43 files. A full redesign cannot be delivered as tokens plus primitives until that is fixed. That pass is frontend-only, behaviour-preserving, verifiable, and belongs in production.
  • Deliver the redesign in layers: tokens, primitives, chrome, then one screen at a time, each its own record and its own port. One long-lived redesign branch against a codebase moving 20 to 50 commits a day would never merge.

Model

How the two repositories relate

The fork shares history with production from the fork commit onward, so a three-way apply resolves against real ancestry rather than guessing. The permanent mock and review infrastructure stays outside src/, while portable token sources, generated styles and product UI changes stay inside the production-shaped tree; a design branch may change portable product files and review-support files, but never protected infrastructure, and only the portable files enter the patch. Production's own plan forbids an in-browser demo mode from ever shipping, and this layout honours that by construction: the mock cannot be ported by accident because it is never in the patch.

Mock layer

How the mock behaves

A service worker intercepts every request the app makes to /v1. The handlers speak the backend's own vocabulary, Prisma state names and all, because the adapter above them expects exactly that. The old design repo's mock spoke the old dialect, which is why its data columns leaked into the PR #2 port. This one cannot.

Route registry and the "no new endpoints" rule

The registry is generated from the pinned backend route map using the same path canonicaliser Atlas uses, so :clientId and {id} collapse the same way. Each handler registers under a key like PATCH /v1/due-dates/{id}. A CI gate fails if any key is not in the map. The reverse report lists the 78 routes the frontend reaches, so the mock's coverage is also checked, and route order is exact-match to avoid the 22 shadowing pairs the real router has.

Two kinds of gap exist and the record must name which. A route that exists in the backend map but that the frontend never wired, of which there are 27 today, needs no backend work but is still an API-surface and product-behaviour change; the record marks it unwired and it needs the developer's approval before port. A route the backend does not have is declared in mock/proposed-routes.json with a reason; the chip shows a red "needs backend" badge whenever it is hit, the record is marked conceptual, and it cannot be marked ready for port. That is the whole enforcement of "no backend changes".

Fidelity beyond route existence

A handler can target a real route and still return fields or transitions the backend never produces. So the mock is tested across the real boundary: each handler's response is fed through the adapter, bundled the way production's own social-login contract test bundles it, and the result is asserted against the minimum screen-facing shape for that resource. Request bodies are validated against the pinned OpenAPI schemas, and the review and submit handlers are checked against the backend's declared state machine using the plans its demo-inventor seed uses. Covered from day one: session user, clients, ideas, drafts, patents, due dates, actions, the evaluation report, invites and share links, upload and import results.

Every record also reports its handler changes: handlers added or changed, routes already wired, routes present but previously unwired, routes absent from the backend, response fields added or changed, and state transitions affected. A handler-only change cannot close a record, and it can never be the thing that makes a broken screen story pass.

Personas mirror the backend seed so a conversation about "the Acme counsel" means the same thing on both sides. The seed has two workspaces, Acme with a tech committee and Globex without, and eight users across all six roles. Every persona gets a realistic portfolio, not the four-patent seed, because the developer's own testing law says an empty table hides broken code.

Things the audit says the mock must get right

  • Answer the login endpoint with the full user shape the adapter wraps, including a real client id for client roles and null for Photon roles, and assigned client ids for case owners.
  • Never answer 401. The refresh interceptor would bounce the app to the login screen.
  • Return 201 where screens assert it: creating an idea, a draft, a client, and the draft patch on the idea details path.
  • Evaluation states are fixed snapshots: queued, running, succeeded, partial, failed, timed out. A story pins one. Only the full app progresses, and it does so on the mock clock, which the chip advances, never on request count, because mounts, focus and strict-mode double effects make request counts unpredictable. The three five-second polls stop when the clock reaches a terminal state with a score.
  • Queries retry every thrown request error three times by default, whatever the status, unless the individual query overrides it; mutations do not retry. Error-state stories therefore use a harness query client with retries off to reach the final state at once, and one parity story keeps production's retry behaviour and checks the loading-to-error delay. The full app keeps production behaviour.
  • Serve files/{id}/raw with an image for any client that has a logo, and accept the raw upload body.
Storybook

Installer discipline

The Storybook installer offers to upgrade neighbours. Run it with the pins above and refuse every upgrade of React, Vite, Tailwind, TypeScript, Playwright or Radix. A gate compares the design manifest with production's plus the tooling set and fails on anything else.

The harness

Most Pulse components do not render from a bare import. They expect the router, the query client, the theme and analysis contexts, the toasters and, for every protected screen, the dashboard chrome: page headers are portalled into slots that only the layout renders. So a screen story mounts a memory router with only its own route nested under the real layout, plus a catch-all route that renders a navigation marker so a play test can assert where the screen tried to go without mounting the destination. There is no second route table to keep in sync; the full app runs production's own App.tsx.

A story selects a scenario rather than building its own data. Its parameters name the scenario, the role and the route. A loader then rebuilds the store, seeds the scenario, clears every known production storage key, writes the session cookie, installs any per-story handler overrides, pins the mock clock, stubs prompt and confirm, marks the frame ready once fonts and the portal slots have settled, and opens the route. Stubs are restored when the story unmounts. A fresh query client is created per story.

Storybook frames share one origin, so the session cookie and both storages are shared between stories. Role-aware stories therefore run serially, persistence is off, screenshot runs use a fresh browser context per story, and parallel execution is enabled only after an isolation test proves two personas cannot contaminate each other: open an inventor story and a counsel story concurrently and assert that each still renders its own navigation and affordances after a refetch.

export const TechnicalReviewQueue = {

  • Auth screens need the Google provider or their sign-in hook throws. The shim provides it, inert, with the same exports; nothing loads from Google and the login endpoint is mocked.
  • Two flows call the browser's own prompt and confirm dialogs. The harness stubs them so interaction tests do not block, and restores them after each story.
  • The sidebar collapses itself under 1440px. Stories declare viewport presets at 1024, 1280 and 1440 by 900, and screenshots are taken at 1440 unless the story says otherwise.
  • The Microsoft and SSO buttons navigate the frame away. Stories show them; interaction tests never click them.
  • The desktop gate keys on pointer and hover media features, not width. Stories that show it use device emulation in the screenshot runner, not a viewport preset.
  • Tailwind only scans src/. Stories compose production components and use no classes of their own; where a harness element needs one, the Storybook Vite config extends the content globs without touching production's config file.

Catalogue

Day one

  • Foundations. Colours, type, spacing, status vocabulary, icons. During the spike and the scaffold these read production's stylesheet and Tailwind config as they are; DSN-0001 introduces the token source, the generator, the generated styles, the font files and the updated foundation stories together, so the scaffold carries no unapproved product change.
  • Primitives. The 29 files under components/ui, every variant and state.
  • Screens. Page stories for every route, for every role that can reach it, default state, using the existing page and workspace components as they are. No production refactor is needed to get here.
  • States. Loading, empty, failure, long content, permission denied, evaluation running, partial and failed, each as a scenario override.

As the work lands

  • Patterns. Page header, filter bar, empty and error states, review decision, evaluation rail, patent summary, client identity. Most of these do not exist as components today; they are inlined in the large screens and appear here as Phase 0 and the redesign extract them.
  • Table. There is no table primitive yet; ten raw tables become one in Phase 0.5, and its stories arrive with it.
  • Per record. Every changed component shows default, loading, empty, error, long content, disabled or read-only, keyboard focus, the relevant roles and statuses, and both viewports.

Two deployments, two origins

The app preview and the Storybook preview are two projects, not one site with a subpath. Each registers its own service worker at its own origin, so neither worker can capture the other's requests, and the app's single-page fallback never swallows a Storybook URL. The design repo's own vercel.json has no API rewrite and a content policy that allows only the local origin. Records link both previews.

Before and after

A story renders the component as it is on its branch, so "current" and "proposed" cannot both be stories in one build, and the design main moves every day, so a branch URL is not a record either. The canonical evidence is what the record commits: the before commit, which is the branch's merge base, and the after commit; the story index; the interaction and accessibility results; the build checksums; and the before and after screenshots. Hosted previews are convenient review surfaces and nothing more, because their retention depends on plan and account settings. Story ids are stable and treated as API: a story an open record names cannot disappear without the record being updated.

Tests that run on stories

  • Interaction. Play functions for dialogs opening and closing, tabs, filters, keyboard access, confirmation, focus return, error and retry, and the fixed evaluation states. Serial until the isolation test passes. They never claim persistence or authorization; production QA owns those.
  • Visual. Screenshots per story in the same pinned Playwright image production's CI uses, taken from the story frame directly rather than the manager, after the ready marker, with vendored fonts, pinned locale and timezone, the mock clock, seeded random and identifier sources, animations disabled, and a fresh browser context per story. Baselines live in the repository; Chromatic is an option later, not a dependency.
  • Accessibility. The axe addon runs on every story and is configured to fail, not only to report. Inherited screens already carry violations, so those are fingerprinted by story id, rule id, impact and normalised element context, never by selector, and the gate is a ratchet: no new fingerprints anywhere, and zero violations inside the redesigned content root of any story tagged for the redesign, so an inherited shell violation cannot block every page.
  • Unhandled requests and egress. The worker treats an unhandled request as an error, and a browser-level block in every runner fails any request to a host other than the frame's own origin. Warnings alone are not a gate.
Rules

Rules the AI agent works under

You work with Codex, the developer works with Claude. Both read AGENTS.md; Claude Code also reads the root CLAUDE.md and scoped rules under .claude/rules/. Production's CLAUDE.md cannot be loaded as instructions here: it says the design must not change, which is right for production and wrong for this repo, and it carries demo hosts, deploy steps and account references an agent must never use from a mock. Contradictory instruction files are not neutralised by a second file sitting beside them, so precedence has to be stated in the file Claude reads first.

The design repo therefore owns its root CLAUDE.md. It states precedence, imports AGENTS.md, and points at production's file, which is preserved and synced as contract/production-CLAUDE.md together with the backend's product rules. The sync reports every upstream change to those files in its commit message so nobody misses a new product rule. The design CLAUDE.md opens with:

Production behaviour rules remain binding. Read contract/production-CLAUDE.md
and contract/production-backend-CLAUDE.md for them.
The production visual-lock rule is suspended only inside an approved DSN record.
Sections of the production file about the demo environment, deployment and
accounts do not apply here. Never call a demo or production service from this repo.

The token source is deliberately portable: it lives in a production path with its generator, so production can adopt it and later token changes travel as one file.

Always

  • Start from the existing component and its props. Restyle in place; rewrite only with a design record that says so.
  • Put colour, type, spacing, radius and shadow decisions in the token source. No new literal visual values in product files.
  • Use the existing primitives under components/ui first. A new primitive is its own record.
  • Keep every role's routes, redirects and affordances. Add a scenario for every new state you introduce.
  • Run typecheck, the role lint, the build, the invariants and the conformance tier before opening a PR. Read the conformance diff before re-recording.
  • Reference the stories that cover every component you change, selecting scenarios rather than building fixture objects. Add a story or a scenario only for a state nothing covers yet. A change without story coverage is not reviewable.
  • Write the design record: intent, what moved, what stayed, the story ids, screenshots per role, backend impact.

Never

  • Touch the adapter, the roles module, auth, analytics or the query hooks from a design branch. Those are behaviour, and behaviour changes go to production as findings.
  • Change protected infrastructure from a design branch: the mock runtime, the route registry and guard, the Storybook config, the harness, the QA corpus, the contract pins, the instruction files. Those change through tooling PRs.
  • Add a dependency, upgrade Tailwind, React, Vite or Radix, or swap a library. Tailwind stays on 3.4.
  • Invent an endpoint, a status value or a role label. Statuses come from the pinned enums.
  • Render an identifier to a reader. Reference numbers only, which a gate enforces.
  • Remove an affordance that authorization depends on to simplify a layout.
  • Re-litigate locked product decisions: the review chain, inventorship, stage gates, one-click view-as, the desktop gate, same-origin uploads, content-free analytics.
Redesign

Delivering a full visual redesign on this codebase

The v4 system is close to complete: three typefaces, an ink and brand palette, hairline surfaces, 2px corners, a navy rail. The gap is not the system. It is that production cannot receive a system yet. Roughly four in five colour decisions are literals inside screens of 1,300 to 3,000 lines, three status-colour vocabularies disagree, 750 dead theme branches obscure every file, and the score-progress UI lives inside a React context. A designer restyling those files directly would produce thousand-line diffs against files the developer edits daily.

Phase 0. Make production themeable

This is developer work, in production, on the frontend only, and every step is behaviour-preserving and provable. Each step is a normal production MR that must leave the conformance baseline identical, including its style projection, and must produce a zero-pixel screenshot difference per role and route. A pixel diff is the wrong tool for detecting change and exactly the right tool for proving there was none.

Why this belongs in production

Production moves 6 to 57 commits a day and the developer touches these exact files for fixes. A refactor of this size done in the design repo would conflict before it could be ported. Done in production, it lands in days, and every later design port shrinks from thousands of lines to the token file and the parts of a screen that actually changed. It is frontend-only, so it sits inside your constraint.

One conflict to settle

The backend's rebuild plan describes a "structured base, glass accents" direction with translucency and blur. The approved v4 sheet is the opposite: opaque, hairline, no shadows. Drift

Staying in sync

Cadence

  • Production is the upstream remote. A sync script merges its main into the design main; a scheduled action can run it. Daily while production exceeds ten commits a day, weekly otherwise.
  • Design branches live under a week. A record older than that is rebased before export, and the export refuses to write a patch whose drift check fails.
  • Conflict resolutions are remembered with git's rerere so a repeated sync does not re-resolve the same hunk.
  • Instruction files never merge, and the sync script is the control, not a merge attribute, because an attribute's merge driver has to be configured in every clone and a repository cannot guarantee that. The script saves the design-owned instruction files, merges production, restores them, sanitises and copies production's instructions into contract/, fails if the design preamble changed, and records the upstream instruction diff in the sync commit so a new product rule is read, not lost. The attribute stays as a convenience for local merges.
  • Production's conformance baseline stays untouched and merges cleanly; the design repo records its own under baseline-mock/, selected by mock mode.
  • QA defaults to mock mode in this repo: local base and cookie sessions, and the inherited login fallback credential is removed from the design copy of the session helper. Inherited files still name outside hosts in inert places, such as the shared contract's demo entry, the analytics host, a legacy download fallback and the page metadata. Those are registered in an allow list of inert references. The rule is that no credential exists anywhere, that no executable request reaches a forbidden host, and that the instruction files carry no usable account.

Pins and freezes

  • Node 22 in both repos, declared in .nvmrc and the package manifest's engines field. The lockfile is installed with npm ci only.
  • No dependency changes on design branches. The manifest and lockfile are protected infrastructure and never enter a patch.
  • Lockfile policy. The design repo keeps its own augmented lockfile. On sync, production's manifest changes are applied and the lock is reconciled with a lock-only install rather than regenerated. A gate then compares the result with production's lock: every production dependency resolves to upstream's version and integrity, the only additions are the approved tooling set, npm ls shows one copy of react and react-dom and no incompatible or duplicate vite on the app and Storybook path, and a clean install reproduces the tree. No blanket overrides; a narrow one is added only when a duplicate actually appears and every consumer's peer range accepts the root version.
  • Stack freeze: Tailwind 3.4, React 18, Vite 5, Radix as pinned. A Tailwind 4 migration, if ever, is a production decision made once, in production.
  • The production baseline commit is recorded in every design record, so a port always knows what it was written against.

Spike exit criteria

The spike is a success only if every line below is proved, and the full scaffold waits for it.

  • The full app and Storybook both render the login screen and the review queue.
  • Portal header actions settle reliably and the ready marker fires after them.
  • Google and every other outside request is blocked at the browser level.
  • Two personas cannot contaminate each other in the isolation test.
  • Fixed evaluation states stay fixed across mounts, focus and reloads.
  • Error stories are deterministic with retries off, and the parity story shows production's delay.
  • Screenshots are identical across two clean runs.
  • An accessibility failure blocks, and an inherited fingerprint does not.
  • The portable patch excludes every design-support file.
  • The patch applies in a disposable production worktree and production's gates pass there.
  • A sync preserves the design instructions and reports a new production rule.
  • The augmented lockfile installs reproducibly with one React runtime.
  • The app preview and the Storybook preview deploy independently.
Decisions

Decisions only you can make

1
Where the design repo lives
Two workable options. A private project in the Photon Legal GitLab group gives organisational ownership and protected branches on the free tier, though enforced code-owner approval needs a higher tier. A private repository under your GitHub account needs GitHub Pro for protected branches, which is enough. A bot check on an unprotected repository is not equivalent: an administrator can still merge, force-push or bypass it.
2
Phase 0 is developer time in production
It is the single biggest lever on port cost and it sits inside your no-backend constraint. It needs the developer's agreement and about a week of their time spread over the redesign.
3
The token truth
The approved sheet says green #1E7B4D and red #B3362F; production ships #2F8D70 and #C96558. DSN-0001 needs you to confirm the sheet wins.
4
Workspace and Actions
The v4 bundle and the v4 screens folder disagree on both. The bundle's org, profile and people workspace matches what production built; the screens' document-drafting workspace does not exist and would be conceptual.
5
Dark mode
Recommended out of scope. The dead dark code goes regardless; the token structure keeps a dark block possible.
6
Preview deploys
A Vercel project on the design repo with no environment variables gives every record a clickable preview. Recommended yes.
7
Node pin in production
Production's CI uses Node 22 but the repo declares nothing; your machine runs Node 25. Both repos should declare 22.
8
The founder tier
Production bounces the superadmin from client detail and labels the role "Member". The redesign will expose both. Decide whether the design fixes them or records them for the developer.
9
Vendored fonts in production
Replacing the Google Fonts link with self-hosted open-licence files is a small production change that makes screenshots deterministic and lets the network gate stay strict. Recommended yes, inside DSN-0001.
10
Enforced approvals on the design repo
Follows from decision 1. GitLab: protected branches on Free, enforced code-owner approval on a paid tier. GitHub: protected branches and required checks on Pro. Decide whether owner approval must be enforced by the host or is acceptable as a required status check.
Risks

What could still go wrong

  • Velocity. Any record older than a week will conflict. The export refuses drifted patches, which is annoying by design.
  • The giants. Even after Phase 0, restructuring the idea-details screen means editing a 3,000-line file with 39 state hooks. Restyle within existing component boundaries; ask for a production split first when the layout itself must change.
  • Partial proof. The style projection samples at most 70 named controls per page. The zero-change screenshot gate covers Phase 0; visual review of the redesign itself stays human.
  • Mock fidelity. Behaviour parity stays production's job. The mock models transitions the screens depend on, not every server rule. A design that relies on a mock-only behaviour is a conceptual record.
  • Tool gates. Figma's code connect needs an organisation plan; Claude Design generates pages that must be transplanted into this repo by an agent, never pasted as new files.
  • One legacy call. The draft-files download still targets the old API host directly. The mock intercepts it; the redesign should not depend on it.
  • CI minutes. Browser tiers plus story screenshots run 15 to 25 minutes. With daily syncs and several PRs a week that exhausts a small minutes budget. Cheap gates run on every push; browser tiers and screenshots run when a PR is marked ready and on main.
